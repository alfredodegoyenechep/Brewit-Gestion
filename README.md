# Brewit-Gestion

Brewit-Gestion is a management dashboard UI for the Brewit coffee shop, covering daily sales, service orders, menu performance, and inventory visibility.

## Project structure

- `index.html` — main dashboard structure.
- `styles.css` — full visual styling for the Brewit-Gestion layout.
- `script.js` — UI behavior for navigation and quick dashboard interactions.

## Local run

Install dependencies once, then start the application:

Use Node.js 20 or later; the web report downloader uses Playwright Core.

```bash
npm install
npm start
```

Visit <http://localhost:3000>. The same server delivers the dashboard, API, and uploaded-file downloads, so a second static server is not required.
After changing server code, stop and restart `npm start`; refreshing the browser updates the UI but does not reload code already held by the Node process.

En **Estadísticas por producto y horario**, cada reporte tiene sus propios filtros de **Cafetería, Período, Desde y Hasta**, y se consulta con **Generar reportes**. Cambiar de pestaña conserva la selección y el resultado de cada reporte; cambiar un filtro requiere generar de nuevo. **Participación** y **Jerarquías y margen** se consultan de forma independiente. **Productos y jerarquías** agrega Barra y Agrupar formatos antes de **Generar reporte**. **Franjas horarias** permite elegir **Inicio período** y **Fin período**, y mostrar **Total** o **Promedio**. En **Día específico** se elige **Fin período** y 1, 2, 4, 8, 26 o 52 fechas del mismo día de semana hacia atrás, incluida la fecha de fin. Se toma esa muestra de calendario sin reemplazar fechas sin venta por semanas más antiguas. Los promedios dividen por los días con venta total distinta de cero: si se piden 8 fechas y 2 no tienen venta, se divide por 6. Los títulos y las tablas indican si muestran totales o promedios. **Clientes recurrentes** contiene **Recurrencia y retorno**, con pestañas **Resumen, Retorno, Compras, Calidad de datos, Evolución 12 meses y Cruces entre cafeterías**. Parte en últimos 28 días completos; Hoy, Semana actual, Mes actual y Personalizado son opcionales. Retorno tiene fechas de primera observación independientes, inicialmente seis meses calendario. Abrir la vista, cambiar filtros y navegar no calcula ni sincroniza: se pulsa **Generar reportes**, **Generar retorno** o **Preparar Compras/calidad** según corresponda. **Resultados Financieros** reúne Resultados Semanales / Mensuales, Estado de resultados, Gastos generales y Revisión de costos. Estado de resultados y Revisión de costos conservan ubicación y fechas independientes; Gastos generales mantiene su matriz por unidad y año.

Uploaded data is stored under `uploads/` and is intentionally excluded from Git. Back up that directory if the local upload history needs to be preserved.

En **Caracterización de la Venta → Horarios y evolución**, el mapa permite elegir **Pedidos** o **Unidades vendidas**. Con filtros de categoría, producto o formato, muestra unidades por defecto y suma únicamente las líneas que cumplen esos filtros, excluyendo extras. Los pedidos siguen contando una sola observación por cuenta: por ejemplo, 24 unidades de bollería pueden corresponder a 18 pedidos. La columna Total del día, la fila Total y los porcentajes usan la medida seleccionada.

El selector **Total / Promedio diario** aplica a ambas medidas. El promedio se presenta con un decimal: cada fila divide por las fechas de ese día de semana con venta total distinta de cero en las cafeterías seleccionadas. La muestra se define antes de filtrar categoría/producto/formato, por lo que una fecha con ventas de otros productos aporta cero al producto elegido. La fila inferior usa todos los días de la muestra para calcular el promedio global, sin sumar los promedios de los días de semana. Un guion indica ausencia de fechas válidas.

**Caracterización de la Venta** permite elegir todas las cafeterías o una cafetería, período, categoría, producto, modalidad, tamaño/formato, segmento de nombre e intervalo de precios. El procesamiento comienza únicamente al pulsar **Analizar**; abrir la vista, cambiar filtros o volver a ella no recalcula el reporte. Las opciones de categoría, producto y formato se cargan con el primer análisis. Los períodos predefinidos usan la fecha de Chile del servidor; **Personalizado** permite indicar desde/hasta. Tamaño/formato usa el campo explícito de venta o los sufijos finales `(CL)`, `(GR)` y `(XTR)` del producto, sin asignar capacidades en mililitros. El filtro selecciona pedidos que contienen ese formato y conserva su canasta completa; al combinar producto y formato, ambos deben coincidir en la misma línea. El análisis muestra cinco etapas y tiempo transcurrido. La API conserva su respuesta JSON habitual y ofrece eventos NDJSON con `progress=1`.

## Upload rules

**Datos y sincronización** organiza el trabajo en tres pestañas: **Estado y actualización**, **Cargar archivos** y **Revisar períodos anteriores**. La primera permite filtrar por ubicación, consultar cada fuente y actualizar una selección explícita. Ventas y pagos se actualizan juntos; los movimientos de inventario pueden incluir tomas vinculadas. La Bodega Principal comparte fuentes con La Concepción y se evita repetir su descarga. Los maestros se presentan aparte, con alcance compartido para todas las ubicaciones. El estado distingue datos guardados, ausencia de datos, procesos activos y observaciones; la fecha de guardado no garantiza que el período esté completo. La matriz comparativa y la actualización global quedan en opciones secundarias.

**Actualizar MercadoPago desde web** está en **Estado y actualización** y abarca todas las cafeterías de la cuenta. **Cargar archivo único de MercadoPago** está en **Cargar archivos**, junto con las cargas manuales por local. La descarga web revisa el **Período de fechas** de los reportes CSV ya disponibles en [Todas las transacciones](https://www.mercadopago.cl/balance/reports/settlement_v2), incluyendo reportes solapados y páginas siguientes. Parte del último día realmente registrado de cada cafetería, inclusive; si no tiene registros, parte del 18 de mayo de 2026. **Revisar períodos anteriores** permite consultar fechas anteriores manualmente. Los identificadores `SOURCE_ID`, `TRANSACTION_TYPE` y `TRANSACTION_DATE`, junto con la cafetería, evitan repetir un movimiento aunque cambie el orden de columnas. Una fila con la misma identidad y contenido distinto se informa como corrección pendiente; se conserva el importe anterior y el archivo original hasta validar cuál reporte debe prevalecer.

El progreso y las solicitudes de autenticación permanecen visibles al cambiar de pestaña. **Ver detalle de carga** conserva los diagnósticos y las opciones avanzadas de ventas y compras. **Abrir Inventario** lleva a la consulta y exportación detallada dentro de Inventario, conservando la ubicación. Las pestañas admiten navegación con flechas, Inicio y Fin; los formularios y las cargas manuales se adaptan a pantallas estrechas.

Si MercadoPago pide autenticación, inicia sesión en la ventana de Chrome que abre el servidor y pulsa **Ya inicié sesión, continuar**. La sesión queda en un perfil privado dentro de `uploads/.integrations/mercadopago/profile`; no se piden contraseñas en Brewit. El enlace a MercadoPago permite consultar los reportes, pero iniciar sesión en otro navegador no autentica ese perfil. Se requiere Chrome instalado en el equipo del servidor, o `BREWIT_CHROME_PATH` apuntando a su ejecutable, y una pantalla disponible para el inicio de sesión.

En la ejecución normal de Brewit, todas las fuentes externas se actualizan solo cuando el usuario lo solicita. Las programaciones guardadas de versiones anteriores quedan inactivas. Si la sesión vence, la pantalla indica que debes autenticarte y continuar. Si no hay un reporte CSV para el período, debes crearlo en MercadoPago y reintentar; Brewit informa hasta qué fecha llegan los reportes descargados. Las filas sin cafetería asociada se omiten y se informa su cantidad. Se validan todos los CSV antes de guardar; una descarga o validación fallida conserva los registros existentes.

- Choose a cafeteria or the main warehouse before selecting transaction files; no week key is required.
- Transaction categories are updated one at a time. Each row shows the most recently uploaded file and provides equally sized, right-aligned Preview, Delete, and Upload New File actions; the former batch “Detect dates and review” action is no longer used.
- “Último archivo subido” expands an inline history of every upload in that category, including filename, upload time, confirmed range, and whether it added records or replaced coincident dates. The separate latest-sales-transaction label is no longer shown on the upload screen.
- After a transaction file is selected and inspected, its detected dates, structure validation, and overlap options are presented in a modal confirmation window. Closing, cancelling, or pressing Escape abandons that pending selection; a successful result is reported back on the upload screen.
- Upload New File opens the operating-system file picker and immediately validates the selected category structure, detects its date range, and opens the existing-data review. No second inspection click is required.
- Each store accepts Kardex, waste, marketing consumption, employee consumption, purchases, sales, Detalle Pagos, and MercadoPago transactions.
- The main warehouse accepts only its Kardex.
- New transaction uploads are stored cumulatively by location and category. Existing week-based folders remain readable as legacy data but are no longer created by the UI.
- Accepted formats are CSV, XLS, XLSX, and TXT.
- Each file is limited to 50 MB.
- Brewit detects the date range inside the staged files and requires user confirmation before saving.
- Before accepting a transaction or master file, Brewit verifies its workbook sheets and required headers against the selected category. Recognized mismatches are blocked with an explicit explanation of the selected and detected file types; valid transaction reviews show an “Estructura verificada” confirmation.
- Detalle Pagos is stored as its own source. Spanish exports with `FechaCierre`, `Comanda`, and `Comentario General` are interpreted as day/month/year; English exports with `DateClosing`, `Ticket`, and `General Comment` are interpreted as month/day/year. Both receive strict structural validation, while other manually uploaded variants remain accepted when readable and non-empty.
- Consumption-mode sales use `A Pagar` in Spanish Detalle Pagos exports and `Due` in English exports as the final gross order amount, normalized to pesos and divided by 1.19 for the dashboard's net-sales basis. The Sales Totals amount remains the fallback when that field is absent.
- Kardex/Merma and marketing/employee consumption share structural families. Brewit uses standard filename and sheet-name signals to catch clear cross-selections while accepting genuinely ambiguous files only when their shared family matches the selected category.
- When uploaded dates overlap existing data, Brewit explains the affected range and asks whether to preserve existing records while adding only new ones or replace the coincident days with the new data.
- Delete offers two explicitly confirmed operations: revert the latest upload, which restores any older dates hidden by that upload, or remove every current and legacy upload for that location/category. The user must type `ELIMINAR` before either operation runs.
- Sales and purchases are de-duplicated by their transaction/document identities. Detalle Pagos omits exact repeated rows. MercadoPago uses movement identities when available and exact rows for older exports; web downloads require STORE_ID, SOURCE_ID, TRANSACTION_TYPE and TRANSACTION_DATE. Kardex, waste, and consumption processing combine all active source dates and honor replacement exclusions.
- “Descargar Ventas desde web” sequentially downloads, validates, de-duplicates, and saves both Ventas Totales and Detalle Pagos, while preserving authentication, restaurant-selection, route fallback, and diagnostics handling for each report.
- The shared master categories are the combined Products / Ingredients / Extras workbook, product hierarchy, ingredient hierarchy, extras hierarchy, recipes, and suppliers.
- Every master requires a “Válido desde” date. A duplicate category/date combination must be explicitly replaced or cancelled.
- Saved masters include an in-app spreadsheet preview and permanent deletion with explicit per-file confirmation.

## Control histórico

**Control histórico**, debajo de **Datos y sincronización**, conserva los originales de cada carga manual, descarga web y sincronización. Ofrece **Cambios del día**, **Respaldos** y **Almacenamiento**, con filtros por fecha, conjunto, origen, ubicación y bodega. Las descargas recuperan los bytes originales; las capturas API conservan sus cuerpos antes de las conversiones de los reportes, sin guardar cabeceras de autenticación ni URLs con credenciales.

Los archivos y reportes se guardan comprimidos en `uploads/.historical-control/`, fuera de la limpieza operativa y con retención indefinida. Cada ejecución conserva su propia evidencia, incluso si no cambia ningún registro. Un fallo al guardar o verificar el respaldo impide publicar los datos nuevos. Las comparaciones corren en un trabajador separado y sus pendientes se recuperan al reiniciar o con la siguiente carga. El cierre del servidor espera las comparaciones pendientes.

La primera recepción válida establece la línea base por conjunto, origen y ámbito. Las modificaciones de registros existentes y las eliminaciones verificadas se muestran separadas de las altas históricas. Las altas del día en curso y las fechas nunca recibidas son crecimiento normal. Los maestros separan sus nuevas altas. Las cargas manuales requieren confirmar explícitamente el período completo y su ámbito para verificar eliminaciones; sin esa confirmación solo se comparan registros presentes y altas clasificables. Las respuestas paginadas o fallidas no reemplazan la última fuente válida. Una identidad o fecha sin resolver deja una comparación parcial o pendiente, sin inventar eliminaciones. Cuando no hay identificadores de línea, se compara el documento con todas sus filas, conservando repeticiones legítimas.

Antes de la primera limpieza se incorporan los antecedentes disponibles. Los archivos reconstruidos desde registros internos se identifican como reconstrucciones: no equivalen al original perdido ni generan alertas retroactivas. Las métricas de almacenamiento suman los tamaños físicos comprimidos, reportes, estados de comparación y metadatos, contando cada archivo una vez. El promedio incluye todos los días desde la activación, incluso días sin cargas; la estimación mensual usa los días del mes seleccionado. El almacenamiento local forma parte de `uploads/` y debe incluirse en los respaldos externos del equipo.

La vista inicial **Alertas** reúne modificaciones, eliminaciones y altas históricas por fecha de detección, con filtros por período, conjunto, origen, ubicación, bodega y tipo. Separa las cargas incompletas y comparaciones pendientes o parciales de los cambios confirmados. Los antecedentes se cuentan sin generar alertas retroactivas; las altas de maestros y el crecimiento normal siguen en **Cambios del día**. El CSV exporta toda la selección, incluidos campos y valores anteriores/nuevos, fechas de operación, versiones y motivos de revisión; la paginación solo limita la pantalla.

La consulta usa `/api/historical-control/options`, `/alerts` (`date`, `dateTo`, `type`, `dataset`, `origin`, `location`, `warehouse`, `offset`, `limit`; `format=csv` descarga el reporte), `/runs`, `/runs/:id`, `/runs/:id/changes`, `/runs/:id/files/:fileId/download`, `/runs/:id/report` y `/storage`, con la protección de acceso existente. Verificación específica: `node --test test/historical-control.test.js test/historical-alerts.test.js test/historical-ingestion.test.js`.

## Location management

- Configuración can create and rename cafeterías or bodegas; the transaction upload selector reads this registry dynamically.
- Cafeterías accept every transaction category, while bodegas accept only Kardex.
- Moving a location to trash requires two warnings and typing its exact name.
- Trashed locations disappear from transaction uploads and both their legacy and cumulative data move under protected `uploads/trash/locations/` storage.
- Restore returns the location and all of its transaction files. There is no permanent location deletion action.

## Sales dashboard

- Ventas is backed by the cumulative sales records and can show all cafeterias together or one active cafeteria.
- All completed-sales statistics use paid prices after discounts and historical costs effective on each sale date, including Vista Grilla, Productos y jerarquías, product analysis, sales by ingredients, Resultados Financieros and the sales margin in Resultados Semanales. The retired `costValuation` parameter cannot change this policy. Inventory balances retain their own balance-date valuation.
- Auditoría Transacciones marks negative amounts/quantities and explicit cancellation, refund, or credit-note labels for manual review. It does not infer physical returns or modify sales automatically, and those flagged orders are not treated as ordinary payment mismatches.
- The headline indicators show net sales excluding VAT for today, yesterday, the current Monday-to-date week, and the current month-to-date period. Day comparisons use the equivalent weekday from the prior week; week and month comparisons use the same elapsed portion of the preceding period.
- A location table separates current day, prior day, week, and month sales. Product rankings and sales participation by product hierarchy can be switched between day, week, and month. Hierarchy participation is interactive: selecting a row drills into its child hierarchy and ultimately lists every sold product ordered by net sales in a scrollable panel, with units, code, share, contribution margin, and a back/breadcrumb control. Contribution margin uses `(net sales excluding VAT - line cost) / net sales excluding VAT`; the sales export's `Costo` is already a line total and is not multiplied by quantity again.
- **Recurrencia y retorno** usa `recurrence.js` para normalizar MercadoPago y compartir una definición: regresar significa comprar en una fecha local posterior a la primera observación. Varios pagos el mismo día suman importes y forman un día con compra. Instrumentos aproximados, días, pagos e importes tienen denominadores distintos; los alias no representan personas únicas.
- **Resumen** presenta activos, activos con regreso, importe identificado de regreso y R30. La evolución permite 8/12 semanas o 6 meses; frecuencia usa 28 fechas completas y recencia 90. **Retorno** incluye a todos los entrantes, vuelvan o no, y muestra seguimiento pendiente, exclusiones por cobertura y bases maduras a 7/14/30 días.
- La cobertura se acredita por fuente mediante descargas publicadas o snapshots verificados; el mínimo/máximo de transacciones no demuestra continuidad. Datos incompletos, estados de pago desconocidos, falta de denominador y seguimiento inmaduro se distinguen de cero. Sin base comparable no hay flechas de variación. Toteat no recorta el historial de MercadoPago.
- **Compras** usa el historial MP para distinguir pedidos de primera fecha y regreso. Uniones ambiguas y pagos mixtos sin atribución comprobada permanecen en **Calidad**. Solo se cuentan productos raíz; importes de pedido, impuestos y propinas conservan su base original. Venta neta es no disponible si no puede verificarse con campos contables; nunca se obtiene dividiendo MP por 1,19.
- La API independiente `/api/sales/recurrence` genera un snapshot con identificador; `/api/sales/recurrence/:id/{summary,return,purchases,quality,monthly,network,details,export}` entrega sus secciones. El worker consulta exclusivamente almacenamiento local, prepara Compras explícitamente y rechaza cambios de versión antes de preparar otra sección. Snapshots en memoria: máximo ocho y una hora de retención. XLSX exporta secciones preparadas con filtros, versiones, cobertura, definiciones y denominadores.
- **Producto-Recurrencia**, después de Clientes recurrentes, tiene cafetería y fechas independientes. Permite agrupar por nivel de jerarquía, filtrar una rama o elegir varios productos por nombre/código. Generar reporte muestra venta neta TotEat después de descuentos y unidades, con tramos **excluyentes 1–15, 16–30, 31–60 y 61–90 días** desde la compra anterior más reciente del instrumento en otra fecha local. Cualquier compra válida de cualquier producto y monto sirve de antecedente; seleccionar productos no limita ese historial ni altera la resolución de vínculos del pedido completo. Cada porcentaje divide por la venta total de su fila, incluidas ventas sin vínculo identificable; se muestran también Sin antecedente ≤90 días observado y Sin vínculo identificable. Solo se cuentan productos raíz, conservando el signo de ajustes de venta. Las ventas posteriores al corte MP siguen en el total sin atribución de recurrencia. Se reutilizan la normalización, identidad aproximada y vínculos de Compras; no se convierte el importe MP en venta neta de producto. La API `/api/sales/product-recurrence/options` carga opciones y `/api/sales/product-recurrence` calcula explícitamente en el worker existente, verificando versiones de ambas fuentes. XLSX conserva importes, porcentajes, filtros, versiones y cobertura; un historial incompleto produce resultados provisionales.
- En **Producto-Recurrencia**, **Agrupar formatos de vaso (CL, GR, XTR)** muestra una sola opción por bebida y jerarquía en el selector. Marcarla incluye todos sus formatos disponibles; activar la agrupación con un formato ya marcado amplía la selección a toda esa bebida, y desactivarla conserva sus tamaños seleccionados. Se puede buscar por nombre, formato o código, y el contador indica bebidas seleccionadas. El cálculo suma importes y unidades antes de recalcular los porcentajes; conserva los códigos de cada formato y separa recetas como hot/iced. Todos los porcentajes de la pantalla y del XLSX se presentan con un decimal, incluidos 0,0% y 100,0%.
- En el reporte por jerarquías se puede abrir cualquier fila hasta llegar a sus productos. La ruta, **Volver** y **Vista inicial** permiten regresar. Los indicadores, totales y XLSX corresponden a la rama visible, conservando la ordenación y los formatos agrupados. El árbol se calcula con la misma clasificación y fuentes del reporte; navegar no vuelve a consultar ni recalcular. Los productos asignados directamente a un nodo se muestran junto a sus subjerarquías para que no desaparezcan importes.
- **Producto-Género** aparece después de Producto-Recurrencia y conserva filtros independientes con los mismos controles, selector agrupado CL/GR/XTR, ordenación por columna, apertura de jerarquías hasta producto y XLSX del nivel visible. Presenta venta neta, unidades y las columnas **Masculino, Femenino y No informado / no identificable**, con porcentaje de venta a un decimal e importe. Usa indicaciones explícitas en las fuentes y asignaciones manuales por pedido. El comentario aporta modalidad, nombre candidato e indicaciones literales; el nombre por sí solo no asigna género. Los campos estructurados `Género declarado`, `Genero declarado`, `Declared Gender`, `Género`, `Genero` o `Gender` de Ventas o Detalle Pagos se concilian por pedido; valores contradictorios, ausentes u otras categorías permanecen en No informado / no identificable. La falta de ese dato se informa en el reporte. `/api/sales/product-gender/options` carga opciones y `/api/sales/product-gender` calcula en el worker existente sin leer transacciones MercadoPago. La agregación y navegación se comparten con Producto-Recurrencia para mantener los mismos totales y criterios de producto.
- **Evolución 12 meses** muestra, para cada mes, el importe MP con una compra previa dentro de 30/60/90/180 días dividido por **todo el importe MP del mes**, incluidos pagos no identificables. Para cada pago se buscan fechas locales desde fecha−h hasta fecha−1; las ventanas son acumulativas. La cafetería seleccionada determina el historial; Todas recalcula la unión. Incluye el mes del corte como parcial cuando corresponda y once meses anteriores, con cobertura de cada ventana y sin usar compras futuras.
- **Cruces entre cafeterías** busca esos antecedentes en **otras** cafeterías de la red. Muestra evolución mensual, detalle por destino y desglose por origen (acumulado o mensual). El total cuenta cada importe una sola vez aunque haya antecedentes en varios locales; los orígenes se superponen y no se suman. Se prepara con **Generar cruces de la red**; navegar o elegir una ventana gráfica no consulta fuentes. El snapshot captura también la versión MP de la red: cambios en otro local antes de preparar exigen regenerar. La identidad entre cuentas sigue siendo aproximada. Ambas secciones exportan porcentajes, importes, denominadores, cobertura y versiones en XLSX.
- Los cálculos antiguos de `/api/sales/dashboard` y `/api/sales/observable-recurrence` se conservan para compatibilidad y conciliación interna. Sus métricas de transacciones y segmentos no equivalen a la definición nueva por fechas. Especificación y evidencia: [recurrencia](docs/auditoria/2026-10-24/Brewit_Especificacion_Reporte_Recurrencia_Codex.md), [validación](docs/auditoria/2026-10-24/RECURRENCIA_VALIDACION.md). Reproducir conciliación local: `node scripts/reconcile-recurrence.js /private/tmp/recurrencia.json`.

## Inventory workspace

- Inventario has its own workspace instead of reusing the general dashboard mockup.
- Selecting an active location shows its latest Kardex, waste, marketing consumption, and employee consumption files, chosen by each file's detected data-through date.
- Cafeterias require all four sources. Warehouses require only Kardex and mark waste and the two consumption sources as not applicable.
- Available sources can be previewed or downloaded, and the update action opens Cargar Archivos with the same location selected. Every inventory-source preview first asks for an inclusive date range, defaulting to the previous Monday through Sunday; Kardex/Merma date groups and consumption date columns are filtered to that range.
- Waste, marketing-consumption, employee-consumption, and processed inventory results open in large scrollable modal windows instead of being appended below the source list. Print/PDF, Excel export, and close actions remain available inside each result window.
- Inventory PDF printing temporarily moves the report out of the browser's modal layer, removes height and overflow limits, paginates every report section and long table, repeats table headers, and keeps individual rows together instead of clipping the output to the first consumption block. The modal is restored after printing.
- In the consolidated Kardex table, Code, Product, Unit, and Unit Cost remain fixed while the movement and balance columns scroll horizontally. Long product names are clipped within the fixed area and remain available as hover text.
- Every consolidated Kardex column can be sorted in ascending or descending order from its header. The table can be searched by product code/name and filtered by total-cost sign or an optional minimum/maximum amount; its visible-row count and total cost update with the active filters.
- The location header no longer carries a shared report range. Processing opens a confirmation dialog with independent opening-balance date/basis, closing-balance date/basis, and inclusive movement dates.
- Defaults are the previous Monday using its opening inventory, the current Monday using its opening inventory, and the complete previous Monday-through-Sunday movement period.
- Merma includes its own inclusive-period summary that consolidates every incoming movement by item, shows unit and total costs from the applicable shared catalog, and hides items whose total additions are zero. MOV-IN and total additions remain visible; other incoming movement columns appear only when their period total is nonzero. A footer totals every visible movement column, total additions, and total cost without incorrectly summing unit costs. Marketing and employee consumption provide equivalent independent-period summaries.
- Spreadsheet previews show up to 400 rows and 400 columns per sheet and indicate when additional content was truncated.
- Merma, standalone consumption summaries, and the complete consolidated inventory report can be printed/saved as PDF or exported as real XLSX workbooks. Consolidated exports place report metadata and each visible table on separate worksheets.
- The workspace enables inventory processing once all required sources are ready and the Kardex date structure is valid.
- Kardex processing detects its dated column groups automatically. Opening and closing balances can each use either the initial or final inventory recorded on their selected Kardex date, while movement columns are consolidated across their separate inclusive range.
- Before consolidating the Kardex, inventory processing builds the Merma additions summary and separate marketing and employee consumption reports over the confirmed movement range.
- In multi-sheet consumption workbooks, the product-structured sheet with the greatest coverage of the selected dates is used. Annotated quantities keep their leading numeric value and non-numeric notes are ignored.
- Each consumption report contains a product summary priced from the applicable shared catalog (falling back to the source workbook only when needed) and an ingredient summary calculated from the recipe master and product/ingredient/extra catalog, including quantities, normalized base-unit costs, totals, and warnings for missing recipes, costs, or unit conversions.
- Ingredient consumption is consolidated into standard units before grouping: grams are converted to kilograms and milliliters to liters, so the same ingredient is shown only once even when its recipes use mixed units.
- Recipe yield is included in ingredient usage and cost: required usage is `consumed products × recipe quantity ÷ (yield percentage / 100)`, before converting and consolidating units.
- For each Kardex item, the report shows its catalog unit cost, selected opening balance, and every movement type consolidated across the confirmed period. Employee and marketing consumption (including recipe-derived ingredient quantities converted to the Kardex unit) appear immediately after the Kardex movements. Both are subtracted when calculating theoretical closing inventory: `opening inventory + Kardex movements − employee consumption − marketing consumption`. The definitive difference is `closing inventory − theoretical closing inventory`, and the total cost is `unit cost × inventory difference`. Kardex quantities use four decimal places, monetary columns use whole CLP, and a footer totals the final cost column without summing unit costs. Negative differences are red, positive values blue, and zero black.

## Financial results workspace

Al pulsar **Actualizar** en Resultados Semanales / Mensuales, un Kardex pendiente por cambios en ventas, compras, tomas o maestros se recalcula con las fuentes locales guardadas. Merma, inventario, consumibles y entradas usan esa misma versión durante la consulta. No se descargan fuentes externas. Si el recálculo falla, las cifras dependientes quedan sin datos y se informa la causa; las observaciones se muestran abiertas y el estado del reporte las destaca. Abrir el detalle diario no recalcula el Kardex.

Los aportes incluyen las comisiones para conciliar con el control neto; un desfase que no pueda explicarse queda identificado, sin crear ajustes o pareos ficticios. El detalle se conserva hasta vencer la consulta y no recalcula fuentes al abrirse.

Other consumables follow employee consumption, then the combined total sums inventory shortage, waste, marketing, employee consumption and other consumables. Percentages use the same cafeteria/period net sales. ## Weekly sales report

Las definiciones oficiales de venta, costo, margen, descuento y ticket promedio se documentan en [METRICAS.md](METRICAS.md). Como regla general, los importes de gestión son netos de IVA; el ticket promedio y los precios observados por el cliente incluyen IVA.

- Resumen General Ventas consolidates the sales files from all active cafeterias; warehouses are excluded.

The classic average card, grid and intraday comparison share the exact eight calendar dates, operating-day rules and cutoff: Santiago wall time for today, complete days for yesterday. Scheduled open zero-sale days count; missing dates without a calendar do not get replaced by older dates. - The intraday section compares today's cumulative sales against the best prior equivalent weekday, the best prior day in the current month, and the best prior historical day. Reference dates are shown in each column.
- Four compact two-column blocks below the intraday section show the latest 14 calendar months, 14 Monday–Sunday weeks, 14 individual days, and 14 equivalent weekdays. Every series ends at the selected report cutoff and follows the cafeteria filter.
- Each historical amount includes a one-decimal variation against the preceding period, shown in blue for zero or positive and red for negative. Daily history compares each date with the same weekday one week earlier; the oldest visible record omits the variation.
- Intraday cutoffs are 08:59:59, 10:59:59, 12:59:59, 14:59:59, 16:59:59, 18:59:59, and 23:59:59. The first row also includes sales before 07:00, and the final row includes every sale from 19:00 through the end of the day.
- Repeated orders found in overlapping uploads are counted once per location using the order ID.

**Probar conexión y guardar** consulta `GET /products` (incluye inactivos). Solo una respuesta válida guarda las credenciales por ubicación. Después, define la fecha inicial en **Ventas y pagos** y pulsa **Guardar configuración de ventas**. Guardar no inicia descargas. **Ir a sincronizar ventas** abre **Datos y sincronización** conservando la cafetería y seleccionando la fuente; allí **Actualizar selección** o **Actualizar ventas y pagos** comprueba el turno e importa ventas y detalle de pagos. **Ver detalle de carga** permite consultar los diagnósticos y acceder a las revisiones completas en **Opciones avanzadas de ventas**.

La actualización automática corre cada 5 o 15 minutos mientras el servidor Brewit está encendido. También puede dejarse manual. Consulta órdenes cerradas, con ventanas de hasta 15 días y solicitudes separadas al menos 21 segundos. Refresca las dos ventanas recientes y el turno abierto, y revisa todo el histórico una vez al día. **Revisar todo el histórico** fuerza esa revisión cuando se necesita recuperar una corrección antigua.

Cada cafetería tiene credenciales, fecha inicial y estado independientes; los locales futuros se agregan desde Configuración y siguen el mismo procedimiento. Una respuesta válida sin ventas muestra **Conectado · sin ventas todavía** y permite preparar el local antes de abrir. Un error de autorización nunca se interpreta como ventas cero.

Las dos fuentes (ventas y detalle de pagos) se publican juntas en `uploads/.integrations/toteat-api/sales/`. Los reportes dan preferencia a las órdenes de API y conservan los archivos originales para el resto del histórico, evitando duplicados. Ante un fallo se mantiene la última versión válida. La fuente API admite vista previa y exportación; no se elimina desde Cargar Archivos. Se conservan las últimas tres versiones completas. La fecha inicial se fija tras la primera carga para impedir cambios que dejen huecos silenciosos.

La equivalencia de detalle tiene límites: no hay fecha/hora de pedido individual ni origen en esta respuesta; el costo viene redondeado y ciertas anulaciones no incluyen productos. Estos campos no se inventan. Los pagos sin productos conservan sus importes y se advierten en pantalla, con identificación en el estado de sincronización y en el XLSX. Las notas de crédito revierten el detalle cuando Toteat lo devuelve con signo positivo. La excepción del extra gratuito descrita en la validación sigue pendiente; no debe usarse esta integración para declarar conciliación exacta de unidades o consumo físico.

El token se guarda con permisos `0600` en `uploads/.integrations/toteat-api/credentials.json`, fuera de las rutas de archivos servidos y excluido de Git. No se devuelve al navegador ni se registran respuestas o errores externos. No está cifrado en disco: proteger este directorio y sus respaldos como el perfil de sesión existente. La aplicación continúa bajo el alcance privado/local descrito en `SEGURIDAD_Y_RESPALDOS.md`.

Para probar de nuevo se puede dejar el token vacío; para reemplazarlo, ingresar el nuevo. Una prueba fallida conserva las credenciales anteriores. Las pruebas se separan al menos 21 segundos en cada proceso del servidor, con timeout de 20 segundos. No se siguen redirecciones HTTP para evitar reenviar credenciales a otro destino; si la cuenta legacy requiere una, habrá que verificar el destino oficial antes de habilitarlo. La base de conexión es fija de producción.

### Compras por API

La misma conexión admite compras con el permiso de lectura `/accountingmovements`. En **Configuración → Integraciones → Compras**, define la fecha inicial de la cafetería seleccionada y pulsa **Guardar configuración de compras**. Luego usa **Ir a sincronizar compras** e inicia la carga desde **Datos y sincronización**. En modo manual no se ofrecen frecuencias automáticas. El panel Compras también tiene **Actualizar compras por API**. Un local nuevo puede conectarse aunque su respuesta todavía esté vacía.

Se consulta `GET /accountingmovements` con `include_sales=false`, compartiendo con ventas la cola de solicitudes separadas al menos 21 segundos. Se actualizan las últimas tres ventanas de 15 días y se revisa todo el histórico diariamente, para recuperar compras ingresadas con fechas antiguas. El botón **Revisar todo el histórico de compras**, en las opciones avanzadas de **Datos y sincronización**, fuerza esa revisión.

El adaptador conserva proveedor y RUT, documento y tipo, SKU, cantidades facturadas y recibidas, ambas unidades y los importes de línea, incluidos los negativos. Usa `sku`, no el identificador interno del producto. Los totales se toman de `total_price`; nunca se reconstruyen multiplicando el precio unitario redondeado. Se conservan por separado la cabecera y las diferencias de suma. El ID de bodega Toteat queda como referencia, sin asignarlo automáticamente a una bodega Brewit.

Toteat también devuelve entradas manuales de caja (`CASH_FLOW`) dentro de la respuesta contable, incluso con `include_sales=false`. Se excluyen del archivo de compras; solo se importan movimientos de proveedores (`PROVIDERS`). Una clase desconocida detiene la actualización para revisión. Si Toteat ha eliminado la identificación de un producto, se conservan sus cantidades e importe con SKU vacío y una advertencia; esa línea no se enlaza a un ingrediente inventado.

Los campos ausentes (usuario, forma de pago, costo negociado, monto neto anterior al descuento y descuento de línea) permanecen vacíos o **No disponible**. La API no permite certificar por sí sola la base neta de costos usada en los controles tributarios existentes. El costo efectivo unitario se calcula a partir del importe de línea y la cantidad, y se conserva además el precio unitario reportado.

Los reportes de compras, referencias de proveedores y costos leen la fuente publicada en `uploads/.integrations/toteat-api/purchases/`. El identificador de movimiento conserva documentos y líneas repetidas legítimas; el cruce por proveedor, tipo y número de documento evita sumar otra vez el archivo anterior. Los números originales se conservan, normalizando ceros iniciales solo para el cruce. Las eliminaciones posteriores no hacen reaparecer documentos desde archivos viejos. Una respuesta inválida, una compra de otro local o un documento sin detalle conserva la última versión válida. Los archivos originales permanecen disponibles como respaldo y se conservan las últimas tres versiones completas de la fuente API.

La bodega de una compra se verifica contra su recepción original (`GET /purchases/`, servicio interno de Toteat), usando la sesión web autorizada. Si `warehouse_receive_ref` selecciona una bodega, esa cabecera prevalece sobre los valores de las líneas. Si la recepción usa “Según bodega de compra de cada producto” (cabecera cero o vacía), se respeta `warehouse_ref` de cada producto. Los códigos se resuelven con el maestro del mismo local: en La Concepción, código 1 es Bodega Principal y código 2 es la bodega operativa del local. Se cotejan identidad, proveedor, fecha, productos y cantidades con `accountingmovements`; una recepción faltante, ambigua, incompleta o inaccesible conserva la última versión completa y muestra el error. Cada sincronización vuelve a consultar las recepciones de todo el histórico cubierto. La sesión web debe estar disponible para esta verificación; el token público por sí solo no expone la cabecera de recepción.

Las cantidades, unidades, fechas e importes originales de Compras se conservan. El Excel registra la bodega efectiva, la bodega contable original y el origen de la asignación. Las capturas contables e internas quedan separadas para auditoría. Las consultas de compras y el Kardex propio usan esa misma asignación; el Kardex se reconstruye al detectar una nueva versión de Compras. `inventorystate` sirve únicamente como comparación y nunca determina la bodega de una recepción. Los históricos se pueden reconstruir desde las respuestas originales, publicando una nueva versión sin alterar los archivos fuente.

Publica las seis categorías juntas en el índice compartido existente, con vigencia desde el día de lectura en Chile y conservando el historial. Todos los locales, bodegas y futuros locales usan estas versiones; las capturas independientes antiguas de Lyon quedan como evidencia y no participan en la selección de maestros.

La actualización consulta JSON de los servicios autenticados de la aplicación web de Toteat; no descarga reportes ni usa el token público de ventas/compras. Es manual mediante el botón y requiere sesión vigente. Los originales completos quedan privados, incluidas recetas y conversiones, y se generan vistas XLSX compatibles para los lectores existentes. La vista previa, descargas y las etiquetas “Última vigencia” muestran la publicación compartida. No modifica los maestros dentro de Toteat.

Si la sesión vence o el navegador configurado ya no responde, el sistema abre y conserva una ventana de autenticación. La actualización queda en **Esperando autenticación**: inicia sesión allí y pulsa **Ya inicié sesión, continuar** para reintentar la etapa pendiente y seguir con el mismo proceso. Los grupos ya completados y los últimos archivos publicados se conservan. Un intento de continuar antes de terminar el ingreso mantiene el formulario abierto. La sesión de recuperación tiene prioridad sobre la conexión anterior mientras su ventana siga abierta.

El piloto del 23 al 30 de agosto está disponible en Configuración y se reproduce con `node scripts/toteat-inventory-pilot.js` sobre las capturas privadas. `--capture` vuelve a consultar las fuentes con la sesión autorizada. No reemplaza aún los archivos operativos del Kardex. Alcance, resultados y diferencias: [informe del piloto](docs/Piloto_Kardex_2026-08-23_2026-08-30.md).

Las fechas son las últimas actualizaciones publicadas, no la fecha del último movimiento. Las columnas, en orden, son ventas, detalle de pagos, MercadoPago, marketing, colaboradores, compras, tomas, transformaciones y transferencias.

Ninguna fuente externa se actualiza por programación en la ejecución normal. El estado también identifica actualizaciones independientes que mantienen ocupado el botón.

## Análisis de clusters de ventas

En **Análisis de la Venta → Análisis avanzado → Análisis de clusters**, selecciona una cafetería o todas y el período. Los filtros seleccionan pedidos completos; las dimensiones activadas y sus niveles de detalle determinan cómo se agrupan. La cobertura mínima inicial es **50 %**. El panel **Parámetros de calidad** permite ajustar todos los umbrales, restaurar los valores iniciales y consultar los valores utilizados en cada resultado. Las preferencias y configuraciones con nombre se guardan en el navegador.

El motor combina composición de productos, horario, calendario, gasto, precio relativo, descuentos, modalidad, cafetería y recurrencia cuando exista cobertura y variación. Utiliza FastPAM/CLARA, muestras reproducibles, validación mediante 20 remuestreos de días completos y 20 referencias aleatorizadas. Una sola dimensión produce segmentación exploratoria; los grupos que no cumplen los criterios seleccionados se presentan como exploratorios. La falta de información no se interpreta como cero ni obliga a generar agrupaciones.

Las tarjetas y la matriz muestran pedidos, venta neta, participaciones, ticket mediano con IVA, productos, horarios y composición por modalidad/cafetería. **Ver detalle y pedidos** abre perfiles y pedidos paginados con todas sus líneas. **Profundizar** permite hasta tres niveles; **Buscar refinamientos** evalúa cambios de jerarquía a categoría/producto y de franja a hora, recomendando solo mejoras con soporte. **Comparar otro período con estos grupos** conserva los representantes y las transformaciones del período base; no vuelve a descubrir los grupos ni certifica su estabilidad en el nuevo período.

Cada variable permite configurar su cobertura mínima entre 0 y 100 % en su tarjeta. Un campo vacío utiliza el umbral general (50 % inicialmente). Los umbrales se guardan con la configuración y se conservan en las comparaciones; restablecer parámetros elimina los valores particulares.

La recurrencia permite elegir compra anterior observada (incluidas compras previas del mismo día, con hora del pago vinculado) o compra en una fecha anterior dentro de las cafeterías seleccionadas y corresponde a instrumentos de pago vinculados, no a personas únicas. La dimensión de género usa datos registrados o asignados en Revisión de género de ventas. Las configuraciones antiguas con nivel `name` se migran a `validated`; la versión del motor invalida resultados del criterio anterior. Los timestamps de MercadoPago con huso explícito se convierten a la hora de Santiago antes del cruce, respetando el horario de verano.

La preparación de las fuentes y el cálculo se ejecutan en trabajadores separados, sin iniciar sincronizaciones de TotEat. Hay un cálculo activo y dos en espera, progreso, cancelación y un límite de tres minutos para el motor. Los resultados con validación incompleta son exploratorios. Las fuentes locales no requieren costo de inventario para este análisis. La caché privada de 24 horas en `uploads/reports/.sales-clusters/` conserva configuración, versión, resultados y pedidos de soporte, incluso tras reiniciar. No guarda nombres de clientes, comentarios de pago ni identificadores de instrumentos. Una nueva sincronización marca los resultados anteriores como desactualizados; los errores conservan el último resultado visible.

Interfaces: `GET /api/sales-clusters/options`, `POST /api/sales-clusters/jobs`, `GET /api/sales-clusters/jobs/:id`, `GET /api/sales-clusters/jobs/:id/result`, `DELETE /api/sales-clusters/jobs/:id` y `GET /api/sales-clusters/jobs/:id/clusters/:clusterId/orders`. Las dimensiones y los parámetros forman parte del cuerpo del cálculo y de la clave de caché. El control de acceso existente también protege estas rutas cuando está activado.

La cobertura de recurrencia de clusters informa pedidos clasificables, no el porcentaje de venta recurrente del dashboard. La revisión de cobertura muestra el período observado de MercadoPago por cafetería y los pedidos sin pagos en la fecha/local, sin coincidencia, con coincidencia ambigua o sin identificador de tarjeta. La cobertura de género corresponde a pedidos con indicación explícita o revisión manual vigente.


### X-ray producto

La pestaña **X-ray producto**, después de **Producto-Género**, reúne todos los formatos CL/GR/XTR de un producto. Sus filtros de cafetería, período personalizado, jerarquía y búsqueda son independientes. Elegir un producto es opcional: sin selección se genera una colección con todos los productos de la jerarquía y sus descendientes, o de todas las jerarquías. La búsqueda solo limita las opciones del selector. Incluye formatos del maestro sin ventas, mantiene separadas las bebidas calientes y frías y solo calcula al pulsar **Generar informe**.

El informe completo se abre en una ventana amplia con índice por jerarquía, subjerarquía y producto. Las fichas se abren a demanda; el PDF y el XLSX incluyen todas, incluso las cerradas. El PDF contiene índice con enlaces internos, marcadores jerárquicos, paginación y retorno al índice. Se comprueba la versión antes de exportarlo y se puede cancelar su preparación. La participación por tamaño solo se muestra con más de un formato y usa unidades de compras positivas válidas del período, conservando formatos sin venta con 0,0 % cuando existe denominador.

El bloque **Margen teórico vigente** usa siempre el maestro y receta actuales, precio de lista sin descuento y últimas compras compatibles de cada ingrediente, incluso al consultar ventas de períodos anteriores. No reemplaza compras faltantes por costos fijos del maestro. El bloque **Venta real del período seleccionado** usa lo cobrado y los costos de cada fecha de venta. Si no puede reconstruirse el costo histórico completo, se admite como respaldo un costo neto positivo registrado en esa línea de venta; ese total no se presenta como un desglose de ingredientes. **Último mes completo** corresponde al mes calendario anterior a hoy, con fechas y cobertura explícitas; compara precio real medio con IVA/neto, costo real medio y margen. La receta muestra por ingrediente y envase la cantidad y costo teóricos vigentes frente a los promedios reales ponderados del último mes. PDF y XLSX conservan esta separación.

La ficha presenta recetas y evidencias de ingredientes principales, referencias teóricas vigentes de precio de lista/costo por cafetería, resultado efectivo de las ventas, seis meses completos anteriores al mes inicial, gráficos de venta neta y unidades, género vigente, franjas horarias, días y acompañamientos. Género/horario/día usan unidades de compras positivas; los acompañamientos usan pedidos únicos con el producto, excluyendo el propio producto y los extras. Bollería y sándwiches se reconocen por sus ramas específicas y descendientes, sin clasificar por el nombre compuesto de la jerarquía padre. Se muestran cada categoría, la intersección (ambas en el mismo pedido) y la unión sin duplicados. Ajustes y devoluciones permanecen en los totales comerciales y se muestran separados del consumo.

En X-ray, los costos de ingredientes, envases y compras se consideran **netos**, conforme a la base declarada del sistema (`net-source-declared`, o el cotejo `net-field-consistent` cuando exista). No se vuelve a descontar IVA a esos costos. La ficha muestra **Precio neto** después de Precio lista vigente con IVA (`precio / 1,19`) y calcula margen sobre ese precio neto y el costo neto completo. Hacer clic en **Costo disponible** abre la receta valorizada por local: cantidades por producto, rendimiento, conversiones, subrecetas escaladas, costo unitario, aporte, origen y fecha. Los componentes finales concilian con el total; los subtotales de subrecetas no se suman dos veces. PDF y XLSX incluyen el mismo detalle. Los faltantes, rendimientos inválidos o conversiones no disponibles mantienen el margen no calculable. Las recetas de referencia no incorporan sustituciones individuales. Los códigos de ingredientes principales están versionados en `product-xray.js`; nuevas bases sin clasificación se informan como incompletas. Un mes sin cobertura y sin observaciones queda sin datos, no como venta cero.

Los **Clusters del producto** se calculan automáticamente al generar cada ficha, con el motor existente y sus umbrales iniciales. Incluyen todos los códigos de la familia y conservan las canastas completas; ventas y tickets de clusters corresponden al pedido completo. Género se habilita sujeto a los controles de cobertura. Cada grupo informa perfil, volumen, separación, estabilidad y comprobaciones; solo se denomina sólido cuando supera todos los controles. Los resultados insuficientes o exploratorios se explican sin forzar clusters. La conclusión descriptiva exige 100 pedidos y 7 fechas para una base suficiente; un perfil concentrado requiere dos dimensiones con ≥50 % de participación y ≥15 puntos de ventaja, con cobertura de género ≥50 % para considerar esa dimensión.

**Alcance, calidad y notas** permanece cerrado por defecto y reúne fuentes, notas, reglas descriptivas, parámetros y cobertura del motor. Ese bloque se excluye del PDF, conservando en las fichas las advertencias esenciales de cobertura y la validación de los clusters. El XLSX conserva fuentes, criterios y diagnósticos completos.

API: `GET /api/sales/product-xray/options`, `GET /api/sales/product-xray` y `GET /api/sales/product-xray/version`. Comparten `location`, `period`, `dateFrom`, `dateTo`; `hierarchy` acepta una ruta JSON y `family` es opcional; sin familia se devuelve una colección ordenada. Admite `sourceVersion` para evitar cambios de fuentes entre selección y cálculo. `progress=1` emite NDJSON con progreso y resultado. Workers aislados admiten cancelación por desconexión; límite de dos cálculos simultáneos y quince minutos para el informe completo; cada análisis de clusters mantiene el límite del motor. La versión incluye ventas, compras, maestros, cobertura, revisiones de género y versiones de reglas y motor de clusters. El filtro aditivo `productCodes` de Clusters acepta varios códigos sin fragmentar pedidos.

El XLSX contiene tablas, recetas, costos, períodos, distribuciones, fuentes y criterios; los porcentajes se exportan a un decimal. Las revisiones de género invalidan la ficha y antes de exportar se comprueba nuevamente la versión.

Pruebas: `node --test test/product-xray.test.js test/product-xray-api.test.js test/product-xray-ui.test.js`.

En **Producto-Género**, la categoría **Extras y adicionales** incorpora su venta neta y la asignación de género del pedido al total general. Permite abrir el detalle y seleccionar extras por código o jerarquía. Las tarjetas de Masculino y Femenino muestran además su porcentaje relativo; la columna **M / F** compara ambos sobre la suma de sus ventas, excluyendo No informado / no identif. Ambos valores suman 100,0 %, se exportan como porcentajes numéricos en XLSX y la columna se ordena por la participación masculina relativa. Sin una base válida se muestran sin dato. Las unidades de extras se separan de las unidades de productos en tarjetas, tabla y XLSX; los filtros restringen los importes a los códigos o ramas seleccionados, sin atribuir extras a bebidas sin un vínculo comprobado.

### Revisión de género de ventas

En **Control y configuración → Revisión de género de ventas** se consulta el comentario original, nombre obtenido, asignación vigente e historial por pedido. Los filtros incluyen cafetería, fechas, estado, disponibilidad de nombre y búsqueda. «Pendientes» incluye registros sin revisión y comentarios modificados; «Todos sin asignación M/F» incluye también las revisiones cerradas como No atribuible o Sin información.

**Exportar registros filtrados** descarga todas las filas del filtro, no solo la página visible (máximo 20.000). Completar `Género asignado` con Masculino, Femenino, No atribuible o Sin información; `Nombre corregido` y `Observación` son opcionales. Conservar Local ID, Comanda como texto, comentario y versión. Al cargar XLSX, pulsar Revisar archivo y confirmar el resumen general antes de aplicar. El resumen cuenta todas las asignaciones nuevas por categoría (Masculino, Femenino, No atribuible y Sin información), las ya aplicadas y las filas sin asignación. No se solicita responsable ni revisión individual de los registros. Las filas vacías se omiten; errores de categoría, fórmulas, IDs numéricos, pedidos repetidos o versiones antiguas bloquean toda la importación. La reimportación idéntica es idempotente. Las asignaciones pertenecen al pedido y local, sin propagación por nombre.

Los análisis se reutilizan por contenido del comentario y versión del extractor en `uploads/reports/.order-comments/analyses/`; las revisiones y su historial, con fecha, archivo y hash (se conserva el responsable de revisiones anteriores), en `uploads/reports/.order-comments/reviews.json`. La carga inicial procesa las fuentes vigentes de todos los locales. En el servidor de producción, nuevas publicaciones de archivos disparan su actualización; el lector de reportes también comprueba las versiones. Si cambia el comentario o un dato explícito, la revisión anterior se conserva en el historial y el pedido vuelve a pendiente. Las revisiones invalidan las cachés de Producto-Género, Caracterización y Clusters; volver a generar un reporte consulta la asignación vigente.

`recorded-name-search.js` reconoce nombres con claves que conservan ñ, tildes toleradas y posiciones originales, y mantiene candidatos y propuestas de corrección separados. `order-comment-analysis.js` comparte modalidad e indicaciones literales contextualizadas. La base de nombres sirve para reconocer texto; nunca asigna género. Las negaciones y contradicciones se conservan como no atribuibles. El reconocimiento y el dato de género tienen estados independientes.

Pruebas del flujo: `node --test test/gender-review-api.test.js test/gender-review-ui.test.js test/recorded-name-search.test.js`.

El dato vigente se resuelve con la misma función en Producto-Género, Caracterización y Clusters: `validatedGender` junto con `genderBasis` y `genderAmbiguous`. Una revisión vigente, incluida una revisión sin asignación M/F, prevalece sobre el dato original. Los identificadores internos `feminine-associated` y `masculine-associated` se mantienen por compatibilidad de filtros, pero se obtienen de esa asignación vigente.

| Reporte o sección | Uso de la asignación vigente |
| --- | --- |
| Producto-Género | Ventas, unidades, porcentajes, jerarquías, productos agrupados y exportación XLSX. |
| Caracterización: resumen y composición | Cobertura, segmentación, mezcla de productos y detalle de pedidos. |
| Caracterización: hipótesis, acciones y análisis avanzado | Trabajan sobre los pedidos del filtro de género activo; no generan una atribución nueva. También se respeta en comparaciones y estacionalidad. |
| Clusters | Dimensión de género, cobertura, perfiles, filtros, profundización y comparación entre períodos. Sin información y No atribuible permanecen sin valor conocido para esa dimensión. |

Tras importar revisiones, las pantallas de Caracterización y Clusters invalidan sus resultados visibles, y Producto-Género solicita regenerar antes de exportar. El servidor invalida las cachés con la versión de las revisiones; Clusters marca resultados guardados como desactualizados e impide profundizar o comparar desde una asignación anterior. Los reportes sin dimensión ni filtro de género conservan sus cálculos habituales. Prueba de integración con el worker persistente: `node --test test/gender-reports-integration.test.js`.

### Presentación a directorio

En **Ventas y resultados → Presentación a directorio**, después de Resultados
Financieros, se elige un mes y se pulsa **Generar presentación**. No se calcula al
abrir la pantalla ni se sincronizan fuentes externas. El trabajo corre en un
worker, con progreso, cancelación y cola de un cierre activo. El visor permite
navegar las páginas y presentarlas en una ventana ampliada.

Cada versión contiene **16 páginas generales + 2 por cafetería incluida**. La
configuración, las fechas de apertura/cierre y la actividad o gastos del mes
determinan los locales; Bodega Principal se muestra solamente en inventario.
Las exportaciones son PDF 16:9 y PowerPoint con textos y geometrías de gráficos
editables. Ambos usan exactamente el modelo de diapositivas del visor, sin
páginas adicionales por desbordamiento. Las tablas extensas presentan rankings;
los datos completos se descargan desde **Alcance, calidad y notas**.

El cierre reutiliza ventas y costos históricos conciliados del estado de
resultados, género revisado, identificación de recurrencia y el motor estadístico
de clusters. Las alertas y acciones usan reglas deterministas versionadas, sin
llamadas a LLM. El costo teórico usa maestros, recetas y compras disponibles al
cierre. Los faltantes se distinguen de cero; un saldo de inventario anterior al
último día se identifica con su fecha y no acredita cobertura completa.

Las versiones se guardan bajo `uploads/board-reports/<uuid>/`: `report.json`,
`presentation.pdf` y `presentation.pptx`, con hashes de archivos y versión de
fuentes. La publicación es atómica; se verifican las fuentes antes y después del
cálculo/exportación. Generar nuevamente crea otro UUID y no reemplaza archivos.
El JSON archivado contiene agregados, evidencia y diagnósticos; no contiene
comentarios de clientes, membresías ni ejemplos individuales de clusters.

Interfaces: `GET /api/board-reports/options`, `POST /api/board-reports/jobs`,
`GET|DELETE /api/board-reports/jobs/:id`, `GET /api/board-reports?month=YYYY-MM`,
`GET /api/board-reports/:id` y
`GET /api/board-reports/:id/export?format=pdf|pptx`.

Validación focalizada:
`node --test test/board-report.test.js test/board-reports-api.test.js`.
